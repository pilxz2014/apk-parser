## 1. 验证方式（本机环境特殊，先说清楚）

本机环境有两个坑，导致不能像平常那样"跑个命令看输出"：

| 现象 | 影响 | 解决办法 |
|---|---|---|
| **Bash 工具不可用** —— `ls` / `wc` / `head` 全部 `command not found`，连 `cd` 都失败（PATH 里缺 coreutils） | 不能用 shell 做任何事 | 全部改用 Read / Glob / Grep 工具 |
| **PowerShell 不回显 stdout**，且 `>` 重定向写出的是 **UTF-16** 文件 | 命令输出看不到；`Read` 工具读 UTF-16 会报 "binary file" | 写一个 Python/Node 脚本，把结论用 **UTF-8** 写进 `tmp/*.txt`，再用 Read 读 |

所以本项目所有验证都是这个套路：

```
写脚本 → 运行 → 脚本把结论写进 tmp/_verifyN.txt（encoding='utf-8'）→ Read 读出来看
```

`tmp/` 下留下的 `verify1..5.py` / `probe_*.py` / `jscheck.js` 就是这个流程的产物，可以复用。

**另一个必须记住的坑：同一文件并行发多个 Edit 会静默丢改动。**
一次批量发 11 个针对 `app.js` 的 Edit，工具全部回了 success，实际只有 2 个落盘。
→ **同一个文件的编辑要一条一条改，改完立刻回读确认。**

## 2. 真机实测结论（Z21 / Android 13 / SDK 33）

### 2.1 `dumpsys package` 在这台 ROM 上是残的

```
实测：dumpsys package <pkg> 只有 85 行（adbkeyboard）、170 行（student.study）
     只输出 Receiver Resolver Table，**没有** Activity / Service Resolver Table
```

**结论：列组件不能靠 dumpsys。** 主路径改成"拉回 base.apk → 本地解析 manifest"。
实测差距：

| 包 | dumpsys 路径 | APK 解析路径 |
|---|---|---|
| `com.android.adbkeyboard` | 1 个（且 `exported` 未知） | 1 个（`exported=false` 准确） |
| `com.jxw.student.study` | 8 个（`exported` 全是未知） | **32 个**（`exported` 真值、intent-filter 完整） |

拉包结果与「签名」「导出 APK」**共用缓存**，所以看过签名列表件是秒开。

### 2.2 `codePath` 是目录，不是 apk

```
codePath=/data/app/~~YlLuDttuxyk-wMh8PGJwGA==/com.android.adbkeyboard-4Bf_nk2Tv3sdivE_EfQmXQ==
```

这是 split 安装的目录布局，真正的包在 `.../base.apk`。
→ `app_detail` 里：`codePath` 以 `.apk` 结尾就直接用，否则去 `pm path` 问，最后兜底 `codePath + "/base.apk"`。

### 2.3 签名：dumpsys 只给哈希，不给证书

```
signatures=PackageSignatures{5b44325 version:2, signatures:[e7c1affd], past signatures:[]}
apkSigningVersion=2
```

`dumpsys` 里**没有**证书 DN / SHA-256 / 有效期。所以两级加载是这样分工的：

| 路径 | 命令 | 实测耗时 | 拿到什么 |
|---|---|---|---|
| 快路径 | `dumpsys package <pkg>` | **0.22s** | 签名方案（v2）、签名标识哈希 `e7c1affd` |
| 完整路径 | `pm path` → `adb pull base.apk` → 本地解析 | **0.37s** | v1+v2、证书 DN、SHA-256/SHA-1、有效期、算法、是否 debug |

注意两条路的"标识哈希"算法不同（快路径 `e7c1affd` 是 dumpsys 的短哈希，完整路径 `16959b9f` 是自算的），
**不能直接比**。界面因此在两者不一致时给一句"值得留意"，而不是断言不一致。

### 2.4 交叉验证：签名确实是真的

设备拉回来的 `cache/apk/RXRJ480607150007/com.android.adbkeyboard__2.apk` 本地解析：

```
subject = CN=Android Debug, O=Android, C=US
sha256  = 16:95:9B:9F:72:74:E0:C1:8A:1D:67:BA:2D:1E:28:44:65:F2:1C:D8:F0:ED:DF:EE:A3:20:81:0E:08:A1:24:56
validity= 2020-07-08T17:00:55Z → 2050-07-01T17:00:55Z
pubkey  = RSA 2048 bits / SHA1withRSA
```

与本机同名 `ADBKeyboard.apk` 的解析结果 **逐字节一致**，`compare_with_apk` 给出 `verdict=same`。

| 7 | `core/launch/components.py` | 组件永远走 dumpsys 回退，**界面上了无痕迹**；且 APK 路径没有 `launchable` 字段 | `_from_apk` 的 `except Exception: return None` 把真实异常（就是 #4 的 ImportError）**咽掉了**；APK 路径也没算 `launchable` | 异常打到 stderr（`APKPARSER_DEBUG=1` 时打全栈）；补 `launchable = exported && type in (activity/service/receiver)` |
| 8 | `web/static/app.js` | **前端整个加载不了**（SyntaxError，白屏） | 13 处括号少一个 / 多一个（深层 `el(card(el(div(...))))` 嵌套里数错） | 用 `node --check` 建语法闸门，逐处修；新增 `tmp/jscheck.js` 精确定位 |
| 9 | `web/server.py` | 浏览器切页 / SSE 断流 / curl 超时时，**控制台吐一整段 `ConnectionAbortedError` traceback** | 断开发生在**读请求行**阶段（`handle_one_request` → `rfile.readline(65537)`），此时**还没进** `_handle`，所以 `_handle` 里那层 `except` 根本兜不住；异常冒到 `socketserver.process_request_thread`，由 `handle_error` 默认打印 | 新增 `class Server(ThreadingHTTPServer)` 覆写 `handle_error`，把 `BrokenPipe / ConnectionReset / ConnectionAborted / Timeout` 静音（只有 `APKPARSER_HTTP_LOG` 打开时才放行）；`Handler` 另覆写 `handle_one_request` 双重兜底 |
| 10 | `web/server.py` | 挂了代理的机器上，**"服务明明活着却判定成没启动"**（探活拿到 502） | `_http_get` 用裸 `urlopen`，而 `urlopen` 默认读 `HTTP_PROXY` —— 本机常驻代理（开发机 / 公司网络 / CI 沙箱都有），`127.0.0.1` 的请求被绕到代理上，代理直接回 502 | `_http_get` 改用 `build_opener(ProxyHandler({}))`，**回环地址一律直连** |
| 11 | `web/server.py` | 单实例探测失效：重复 `start()` 会在同一端口起**第二个服务** | `_is_port_free` 给探测 socket 设了 `SO_REUSEADDR`。**Windows 上它的语义是"允许抢占"**，能 bind 一个已被监听的端口 → 该函数恒返回 True，"被占"和"空闲"再也分不出来（原先靠后面的 `alive()` 探活把问题盖住了） | 去掉 `SO_REUSEADDR`，让真 bind 探测说实话；再配合"端口空闲就跳过探活"的快速路径（冷启动 1.5s → **89ms**） |

> #9 是噪音，#10/#11 是实打实会让功能错的。#11 尤其典型：**一个恒返回 True 的判断函数，
> 会把所有依赖它的逻辑一起带错**，而它的错误又被另一层补救逻辑掩盖着 ——
> 改上层时必须回头确认下层的前提还成立。

> #15 的教训：**别在 bat 里写非 ASCII 字符，哪怕注释**。代码页是解析期行为，
> `chcp 65001` 只对"之后输出的内容"可靠，对"批处理文件自身被怎么解读"不可靠 ——
> 同一个文件里既有 chcp 又有中文时，两条规则会互相打架。正确分层：bat 只做
> ASCII 胶水，所有人类可读文案归 Python。

### 追加（v0.1.3）：web 端 APK 路径三连问题 + 拖拽载入

用户报的三个现象，逐个查证后结论如下。

| # | 现象 | 结论 | 处理 |
|---|---|---|---|
| 16 | 点「解析」永远是 **`解析失败：文件不存在：{}`** | **是真 bug**：`app.js` 里 `onGo: (p) => doParse(host, p)` —— `doParse` 只接受一个参数，`p` 收不到，`p` 位置拿到的是**渲染用的 DOM 元素**。`JSON.stringify({path: div})` → `{"path":{}}` → 后端 `str({})` = `"{}"` → 「文件不存在：{}」 | ① 调用点改回 `doParse(p)`（`q.path` 那处同样错，一并修）；② 后端 `_valid_apk_path` **对非字符串参数单独报错**：「路径参数类型不对：收到的是 dict」—— 这类错以后再也不会伪装成"文件不存在" |
| 17 | `POST /api/apk/analyze` 报 `TypeError: cannot unpack non-iterable NoneType object` | **是真 bug**：handler 用 `ctx.q("path")` 只读 **query**，POST 走 body 时永远取不到 → 抛 `TypeError` 冒到 dispatch，连错误包装都撑不住（返回的 `None` 让 `status, payload = out` 解包炸掉） | 抽出 `_path_arg(ctx, *names)`：**body 优先、query 兜底**，`parse/analyze/signature/icon/diff` 全部改用它；`analyze`/`signature` 同时注册 GET+POST |
| — | "选下载目录下的 APK，路径多了 `Backup`" | **不是 bug**：注册表 `Shell Folders\{374DE290-…}` 显示这台机器的「下载」被**重定向**到 `D:\Backup\Downloads`（`D:\Downloads` 并不存在，目标文件实测就在 `D:\Backup\Downloads\jxwgb_teacher_app.apk`） | ① 文件框返回后**归一成正斜杠→反斜杠**（tkinter 给的是 `D:/…`，看着像被改过）；② 选中后立刻 toast「已选中 xxx · 24.1 MB」，用文件名+体积自证是哪个文件；③ 记住最后目录，下次弹框直接落在那里 |

**新增能力：把 APK 拖进浏览器直接解析**（用户第 3 条需求）

浏览器**不给**拖入文件的真实路径（`File.path` 是 Electron 私货），所以：

- 前端拿 `DataTransfer.files[0]` 的 `name / size / lastModified` 打 `POST /api/apk/locate`
- 新增 `core/apk/locate.py`：在 `paths.known_dirs()`（**注册表读出的**桌面/文档/下载/图片，
  所以重定向目录也覆盖）+ 项目目录 + 上次使用的目录 + 配置 `locate_dirs` 里搜，
  按 **文件名精确 + 体积精确** 判定命中，体积用于排除同名异文件；限深度 5、限条目 6 万、限时 4s
- 实测：命中耗时 **43ms**（扫 7437 项），搜索根 5 个；找不到时明确提示改用「浏览…」

其他细节：
- 文件对话框改**写临时文件回传**（不再走 stdout）—— 子进程 stdout 编码随环境变（UTF-8 模式 / GBK），
  中文路径过管道必被搅；顺带用 `initialdir` 落在上次目录。实测中文路径 `…\apkparser-中文目录测试\测试应用_学王书房.apk` 无损
- 拖拽遮罩 `#drop-mask`：拖到窗口任意位置都显示"松开载入"，避免用户以为拖不进去
- `start()` 补 `port` 字段；**显式指定另一个空端口时不再被单实例逻辑抢走**（自动化测试需要多开）
- 顺手修 `app.js` 里 `sig.digestIdentity` → `sig.identity`（老键名，签名标识那一行一直没显示）


### 追加（v0.1.4）：右键子菜单始终不展开 —— #14 的修法是错的

用户反馈：`sys menu install` 报成功，但右键「APK 工具」**依然没有子菜单**。
这直接推翻了 #14 的结论 —— 得回去看官方文档原文。

| # | 位置 | 症状 | 根因 | 修法 |
|---|---|---|---|---|
| 18 | `platform/menu_win.py` | 「APK 工具」有级联箭头，但子菜单**永远是空的**（#14 改完仍如此） | **机制用错了。** `SubCommands` 里列的名字**不是**在 `<菜单根>\shell\<名字>` 下解析，而是在<br>`HKLM\Software\Microsoft\Windows\CurrentVersion\Explorer\CommandStore\shell`<br>里解析（只认内置 `Windows.xxx` 谓词，或 HKLM 下注册的静态谓词）。所以 #14 那句 `SubCommands="01info;…"` 等于让 Explorer 去 CommandStore 找 `01info` —— 找不到 → 菜单空。自定义子项的正道是 **`ExtendedSubCommandsKey`**：它是一个**值**，内容为**相对 `HKEY_CLASSES_ROOT` 的键路径**，该键的 `shell` 子键里装着子项。<br>另外还漏了一条官方硬性规定：**级联菜单根的 `(Default)` 必须留空（未设置）** —— 原代码正好设了它。 | ① `SubCommands` 整个删掉；② 设 `ExtendedSubCommandsKey = SystemFileAssociations\.apk\shell\APKParser`（自引用，子项就在菜单根自己的 `shell` 下）；③ 清掉 `(Default)`；④ `install()` 改成**先整棵删旧树再重建**，避免上一版的错误键值残留（`SubCommands` 优先级更高，留着会继续把子菜单压空） |

**这次是怎么查出来的（值得记下来的方法）**：

1. 先把注册表**整棵树 dump 出来**和官方范式逐条对照 —— 发现结构"看起来对"，说明问题不在"有没有写"，而在"机制选错了"
2. 回去读官方原文（`SubCommands` 那篇的 **Step 4** 明确写要往 **CommandStore** 里填谓词）→ 机制错误确认

**组件写法的唯一真相（#20 的修法）**

`am start -n` 的写法只有两种合法形式，`ComponentName.unflattenFromString` 只对**以 `.` 开头**的类名补包名前缀：

| 输入 | 拼出的 `-n` | 说明 |
|---|---|---|
| `com.foo/.ui.MainActivity` | 原样 | 最 idiomatic |
| `com.foo/com.foo.ui.MainActivity` | `com.foo/.ui.MainActivity` | 全限定类名自动缩写成前导点形式 |
| `com.foo.ui.WifiListActivity`（裸类名，无斜杠） | `com.foo/.ui.WifiListActivity` | 靠 `pkg` 提示或**设备已装包名集合做最长前缀匹配** |
| `com.android.settings.homepage.SettingsHomepageActivity` | `com.android.settings/.homepage.SettingsHomepageActivity` | 只能靠设备包名集合 —— 纯字符串猜会猜成 `com.android.settings.homepage` |
| `com.foo`（纯包名） | `com.foo/.MainActivity` | `cmd package resolve-activity` 查 launcher；`am` 没有"启动某包首页"的语法 |

配套的三道闸门：

1. `as_component(pkg, cls)` —— 拼 `pkg/Class` 的唯一实现，不会再有人拼出 `pkg/WifiListActivity`（无包名类名，必然 `Unable to find explicit activity class`）
2. `Intent.resolve(device)` —— **预览和执行走同一段补全**（预览空、执行报错的割裂从此消失）
3. `Intent.validate()` + `start_component` 提前返回 —— 什么都定不下来时 `ok=False`、命令字段为空，并且**一条 adb 命令都不发**。以前那种"跑条空命令还报成功"的行为被彻底堵死

界面侧：组件清单直接用后端给的 `target` 字段；跳转 Intent 页时把 `pkg` 一起带上；预览条在有 `problem` 时顶部挂警告；目标组件输入框下面写清三种写法。

**怎么证伪的（`tmp/dev20.py` 对照实验）**

对真机 `com.android.settings` 的 378 个组件：

```
旧行为（只传 name，无 pkg）→ args=[]                              ← 就是线上那条裸命令
新行为（传 name + pkg）    → ['-n', 'com.android.settings/.Settings']
```

`tmp/verify21.py` 再走一遍 Web 链路（含真机真启动）：`TotalTime=1268ms`、`component=com.android.settings/.Settings`。
其中"旧前端 payload"（只传 name、不带 pkg）也单独测了 —— 现在同样能得到正确的 `-n`，因为设备包名集合能兜住。

已补齐全部规则（含 `.combo-panel` / `.combo-panel.open` 这对**开合机制**），
并新增 `tmp/gate26.py` 把这条约束变成**自动审计**：

```
① 前端用到的每个 class 字面量，style.css 里必须有规则
② 前端 fetch 的每个 /api/...，routes.ROUTES 里必须注册
③ 每个 tab 能力都有渲染器，且父页都走 mergedPage（否则 tab 条根本画不出来）
```

> 判据只有一句：**只有类名、没有规则 = 静默失效**。写完前端构件记得跑 gate26。

#### 审计器自己先被假 FAIL 骗了三次（方法论）

第一次跑 gate26/verify24 出了 6 个 FAIL，逐个查下来**全是审计脚本自己的错**：

| 表面现象 | 真相 |
|---|---|
| "前端在调 `/api/apps/`，后端没注册" | 前端用的是模板串 `` `/api/apps/${pkg}` ``，正则截断在 `$` 上了 → 这类要按**前缀**匹配 |
| `/api/fs/ls` 的 `crumbs[-1].name` ≠ 当前目录名 | 响应里**根本没有**顶层 `name` 字段（前端也不读它）→ 该比 `crumbs[-1].path == path` |
| 历史响应没有 `items` | 键叫 `history`（前端读的也是 `history`） |
| "往返后 amArgs 里 extras 丢了" | **是我把 extra 的字段名写错了**，见下 |

> **教训（重要）**：审计器在用来**否定**某件事之前，必须先用"已知成功 / 已知失败"的样本校准
> —— 这次 `verify24.py` 在开头加了一条**故意失败**的自检断言（确认 `check()` 真的会判 FAIL
> 且不污染计数），否则整份报告可能只是空转。

#### 顺带查明：extras 字段名写错会"静默丢参数"

`Intent.to_am_args()` 里对每个 extra 都有 `if e.key:` 护栏 ——
**宁可不发，也不发 `--es "" ""`**（这个护栏是对的）。但副作用是：
extra 的结构若写成 `{"k":…,"t":…,"v":…}`，`Extra.from_dict` 会把 `key` 读成空串，
于是**这条参数在命令里凭空消失，且全程没有任何报错**。

- 规范结构是 **`{"key": …, "value": …, "type": …}`**（已钉进 `verify24` 的断言）；
  查过 `app.js` 存的正是这个结构（`{ key: x.key, value: x.value, type: x.type }`），
  所以**线上路径没问题**
- 但这条对以后改前端的人是陷阱 → 已在断言里显式钉住字段名

本轮数字：**68 条路由 / 34 个能力（18 个合并进 5 个父页，侧栏可见 16）/ 53 条 CLI 子命令**。

### 追加（v0.2.1）：右键「解析 APK 信息」什么都没弹

**现象**（用户原文）：选中 apk → 右键菜单 → 解析 APK 信息 → cmd 控制台一闪而过，
**没有报错信息，也没有弹出详情信息**；"本来还正常的"。

**根因**：`apk popup` 探测到主控台**进程**活着（`server.json` 有记录 + `/api/health` 200），
就把卡片 `POST /api/popup/info` 进去，然后 `--quiet` 静默退出（rc=0）。

问题在于——**"推给主控台"只有在主控台页面真的开着、并且在轮询时才看得见**。
页面没打开时，那次推送进的是一个没人读的内存列表，浏览器里什么都没有。
而 rc=0 让 `apk-info.cmd` 的 `if errorlevel 1 pause` 不触发，于是连窗口都留不住。

一句话：**代码用"进程活着"当成了"有人在看"**。这两件事差别很大 ——
上桌前一个实例（v0.2.0 的预览）留下了常驻主控台，就把这条路径从
"没有服务 → 打开浏览器卡片"（看得见）静默切成了"推给看不见的地方"。

**修法**（3 处，核心是"看不见就退回必然看得见的那条路"）：

| 位置 | 改动 |
|---|---|
| `web/routes.py` | `/api/popup/pending` 在**页面可见**时刷新 `_UI_LAST_POLL`（它同时是**心跳**）；`/api/health` 多返回一个 `uiAgo` = 页面距今多少秒没来取过卡片 |
| `ui/popup.py` | `server_endpoint()` 返回值加上 `uiAgo`；`show()` **只在 `uiAgo ≤ UI_WATCH_WINDOW`(10s) 时才推**，否则走浏览器卡片，并在文案里说明"主控台在跑，但页面没打开" |
| `cli.py` | `cmd_apk_popup` 解析失败时返回 **rc≠0**，让 `apk-info.cmd` 的 `pause` 停住窗口 —— 否则错误信息跟着黑窗口一起消失 |

配套（`web/static/app.js`）：轮询时把 `document.visibilityState === 'visible'` 一起报上去；
`S.pushSince` 初值从 `0` 改成 `Date.now()/1000`。
用 `0` 的话每打开一次页面就会把服务端留着的最近 20 条历史推送**全部重放**
（连弹 20 个提示 + 20 次跳页）。另外"认不出来的推送"现在会 `toast` 说明，
不再静默跳过 —— 后端字段名一改（如 `path` 写成 `filePath`）卡片就静静消失、
前后端都一片安静，只剩用户"点了没反应"。

#### 第二层：改完"心跳"以后仍然推给了空气 —— 「在轮询 ≠ 看得见」

第一版只按"最近 10 秒内有没有人来取过卡片"判断，实跑验证时**还是没弹卡片**。
量了一下 `/api/health` 的 `uiAgo`（每秒采样一次，只读 health 以免干扰心跳）：

```
uiAgo 从 37 一路涨到 53（连着 16 秒没人来取）
然后被重置成 0.19，接着又一路涨到 7.2，再没被重置
```

即：**确实有东西在轮询，但节奏是 30~60 秒一次** —— 那是一个**被浏览器节流的隐藏页面**
（切走的标签页 / 藏在窗口后面的预览面板）。它偶尔也会落进 10 秒窗口里，
于是卡片又被推进了一个没人看的页面，老问题换了个马甲。

所以判据必须是 **「页面可见（`document.visibilityState === 'visible'`）** 并且在轮询**。
隐藏时照样回 `items`（不然切回来会漏卡片），只是**不刷新心跳**。
前端没报 `visible` 时**保守处理**（当成没人看）—— 宁可多弹一张卡片。

改完后同一个实跑：`uiAgo = null` → `apk-info.cmd` 1.3 秒返回 rc=0 →
**卡片真的生成并交给了浏览器**（16.5 KB，含包名 / 签名区块 / SHA-256）。

**几个刻意的选择**：
- `uiAgo` 从没轮询过时返回 **`null` 而不是 `inf`**：JSON 没有 Infinity，
  `json.dumps` 会写出裸 `Infinity`，浏览器 `JSON.parse` 当场抛 ——
  "当前没有页面在看"是完全正常的中间状态，不该炸掉整条探活链路
- 窗口取 **10s**（轮询间隔 2.5s 的 4 倍）：浏览器会限制后台标签页的定时器
  （Chrome 隐藏 5 分钟后降到每分钟一次），阈值太紧会出现"页面明明还开着、
  却还是弹了张卡片"的抖动。**宁可多弹一张卡片，也不要推给空气** ——
  看得见优先于"体验统一"
- 推送成功时**不**额外去打开浏览器（不重复打扰）

**验证**：新增 `tmp/verify25.py`（**43 PASS / 0 FAIL**），覆盖：
① 死服务 / `uiAgo=null` / `uiAgo=40` 三种"看不见"的情形**都必须**退回浏览器卡片
且**一条都不 POST**；② `uiAgo=1.2` 才推，且推的是含 `path`/`package` 的规范数据；
③ 阈值边界（10.0 推、10.5 退）；④ `uiAgo` 可被严格 JSON 序列化；
⑤ **可见性闸门**：`visible=1` 的轮询才刷新心跳，`visible=0`（含前端没带该参数的
老前端）**一律不算有人看**，但仍然要回 `items`；
⑥ 真主控台（临时端口）上 `/api/health` 的 `uiAgo` 会随"可见轮询"从 `null` 变成 ≈0，
而"隐藏轮询"之后**仍然是 `null`**；
⑦ 解析失败 rc≠0，且经 `apk.cmd` 传出来仍然是 rc≠0；
⑧ 前端确实把 `visibilityState` 报了上去。

> 测试全程 monkeypatch `shell.open_url`（不真的弹浏览器）与 `paths.server_file()`
> （不动用户真实的 `server.json`，用完还原）。

### 追加（v0.2.2）：解析结果改覆盖 + 双击安装支持 -t/-r/-d（带降级确认）

两条用户反馈，各自都是一个真 bug。

#### #35 解析 APK「信息」是追加显示 —— 旧结果永远删不掉

`parseOwnTab.doParse()` 每次解析前会清一次旧结果：

```js
$$('.card.dyn', host).forEach((e) => e.remove());   // ← 选择器对不上任何元素
```

`card()` 造出来的元素只有 `card` 类，而结果容器只带 `dyn` 类 —— **没有任何元素同时
带这两个类**，所以这句清理从来没删到过东西。解析两次页面上就有两份「概览」，用户
看到的是"越点越长"。

改法不是"把选择器修对"，而是**取消"靠选择器去捞旧节点"这种写法**：页面上只留一个
结果容器 `out`，每次解析 `out.innerHTML = ''` 后重新填。顺带加了 `seq` 守卫 ——
连点两次时慢的那个响应回来不能覆盖新的结果（`if (mine !== seq) return;`）。

> 这类 bug 的特点：**代码看着完全正常**。所以验证方式也换掉了：`tmp/verify26.js`
> 把 app.js 里**真实的** `parseOwnTab` / `apkInfoView` 抠出来，配一个 20 行的假 DOM
> 真跑，然后数页面上有几份「概览」。同一份测试里还跑一遍**旧实现**当对照组 ——
> 旧实现必须数出 2 份（证明这测试抓得住这个 bug），否则整份报告都不可信。

#### #36 双击安装：没有 `-r`，遇到降级只会硬失败

`install one` 只有 `--no-reinstall`（`-r` 是默认行为但**没有这个flag**），照着
`adb install -t -r -d` 的写法敲会直接报参数错。而且"版本比设备低"只会返回失败 +
一句提示，用户得自己再加 `-d` 重来一次。

改：
- `-r/--reinstall` 与 `--no-reinstall` 做成**互斥组**（同时给会明确报错，不静默取其一）
- 新增 `-y/--yes`：遇到降级不再询问
- **降级先问再装**：`cmd_install_one` 拿到结果后判定"是否**纯粹**被版本降级拦下"
  （判据是预检项里的 `code == INSTALL_FAILED_VERSION_DOWNGRADE`，**不是**去 parse 文案），
  命中就摆出包名 + 两个版本号问一句 `[y/N]`；按 y 自动带 `-d` 重装，按 n 报"设备没有
  任何改动"并 rc=1
- 判据刻意取"纯降级"：只要有一个文件是别的原因（如签名冲突）失败，就**不问**、也不
  替用户加 `-d` —— `-d` 对整批文件生效，会把别的冲突一起放过去
- `apk-install.cmd` / `apk-install.sh` 原来写死只取第一个参数（`"%~1"` / `"$1"`），
  额外参数在路上就被丢了；改成 `%*` / `"$@"` 透传，于是
  `apk-install.cmd "a.apk" -t -r -d` 这种写法才真的能用
- `--console`（独立窗口）分支补上 `-t/-r/-d/-y` 的透传

顺带修掉一个真瑕疵：`_render_install` 回显命令时读的是不存在的键 `command`
（installer 的结果里叫 `commands`），于是每次都打出一行空的 `$ `。

**验证** `tmp/verify26.py`（52 条断言）+ `tmp/verify26.js`（8 条）：参数解析/互斥、
预检的降级项带 `package`/`versionCode`/`deviceVersionCode` 结构化字段、决策矩阵
（纯降级 / 混合 / 已成功 / 无预检 / 无设备）、六种交互分支（y / n / `-y` / 非 tty /
已给 `-d` / 其它阻塞）、`--console` 透传、薄壳透传、以及真 CLI 的 smoke。

> 交互分支全部用打桩的 `installer.install` 驱动，**不碰设备**；`_can_prompt()`
> 用 `sys.stdin.isatty()` 判断，所以管道/CI 调用时不会卡在等输入上。

### 追加（v0.2.3）：双包对比改成"两侧都能点选 / 都能来自设备"

需求原文：「双包对比，通过文件夹选呀，然后也可以支持与设备 app 对比」。
原来的「双包对比」是两个纯文本框，得手打两条路径，而且只能比**两个本机文件**。

#### 关键决策：设备那一侧**不把整包拉下来**，而且必须与本机**同源**

`remote.py` 早就有一个按需读取器（`AdbRangeFile`：把 `adb exec-out dd` 包成
file-like，直接喂给 `zipfile`）。这次把它接到了**完整解析**上：

- `core/apk/info.py` 抽出 `_read_into(info, reader)` —— "reader → ApkInfo"的**唯一**
  实现，`parse_apk`（本机）和 `parse_apk_reader`（设备）都调它
- `core/apk/remote.py` 加 `parse_remote_apk(serial, path)` → 走上面那条
- 新建 `core/device/compare.py`：`diff_sides(a, b)` 支持**任意组合**
  （本机文件 / 设备应用），设备侧默认按需读取、失败才 `adb pull` 兜底

**为什么"同源"是硬要求**：两侧必须由同一个解析器、同一套字段产出。否则界面上
那些"差异"里会混进解析器差异 —— 用户看到的是包不同，其实是数据来源不同。
这条不是靠自觉，是靠代码结构（只有一份 `_read_into`）保证的，
并在验证里用**自比**钉死：同一个包，设备侧解析 vs 本机解析，10 个字段必须全同。

**刻意不做的两件事**：

| 不做 | 为什么 |
|---|---|
| 用 `dumpsys` 拼一个"半个 ApkInfo"来比 | dumpsys 给的是**已授予**权限、系统筛过的组件子集、没有体积构成。拿它跟本机 APK 比，差出来的全是"来源不同"而不是"包不同" —— 结论会骗人，而且骗得很像真的 |
| 吃 `cache/apk/<serial>/<pkg>__<vc>.apk` 里的现成包 | 缓存键里只有 `versionCode`。开发期最常见的一幕恰恰是"**同一个 versionCode 重新打个包**"（换签名/换渠道），命中缓存会拿旧二进制去比，给出"完全一样"这种最危险的错误结论 |

实测（真机 Z21，33.3 MB 的包）：设备侧解析 **6 次 adb 调用、搬 4.5 MB（13%）**，
约 0.8 s；同一份包 `adb pull` 要 1.2 s 且搬整包。**省的是搬运量，不是侥幸。**

#### 接口：一侧的三态

`POST /api/apk/diff` 里每一侧有三种写法（`a`/`b` 是文件，`aPackage`/`bPackage` 是设备包）：

| 传法 | 含义 |
|---|---|
| `{a: "D:/x.apk"}` | 这一侧 = 本机文件 |
| `{aPackage: "com.x"}` | 这一侧 = 设备上的 com.x |
| `{aPackage: ""}` | 这一侧 = 设备，**包名用另一侧推出来**（"跟它的同名应用比"） |

**"键不存在"与"键存在但为空"必须分开**，所以路由用 `ctx.field(..., None)` 取值：
`None` = 没声明来源，`""` = 声明了设备但包名待定。两者混成一个的话，
"跟同名应用比"这个最常用的动作就没法表达了。

`{a, b}`（两个路径）走原分支，响应与改动前**逐键相同**（有断言守着）。

#### 顺手修掉的：缺一侧时提示不指名道姓

只传 `{a}` 时，`{b}` 会被当成"路径为空"，报出来的是
「路径为空：请先用「浏览…」选择 APK」—— 调用方根本看不出是自己漏了 **B**。
现在两侧分别检查，直接说"B 侧没填"。

#### 前端

「双包对比」页改成：A/B 两侧各有「本机 APK / 设备应用」分段开关 ——
选文件走「浏览…」（原生对话框 → 浏览器兜底），选设备走**包名自动补全**
（`pkgCombo`，数据来自 `/api/apps`）。B 侧包名留空 = 与 A 的同名应用比。

结果区除了原来的字段/权限/组件/签名表，多出三块：**两侧来源**（谁来自哪、设备序列号）、
**设备侧读取代价**（几次 adb / 搬了多少，让"没整包 pull"可验证）、
**设备侧安装信息**（安装器、是否系统应用、首装/更新时间）。split 安装、两侧包名不同
这两种"看着像对比其实不是"的情况会给出显式提醒。

**验证** `tmp/verify27.py`（**60 条断言**）+ `tmp/verify27.js`（20 条）：
① 老契约逐键相同；② 一侧三态 + 反向（A 设备/B 文件）+ 两侧都是设备；
③ 搬运量 < 整包 50%、adb 调用 ≤ 40；④ **同源自比 10 字段/权限/组件/签名/体积全同**；
⑤ 坏序列号 / 空侧 / 双侧空包名都给结论不抛异常；⑥ CLI 四种形态；
⑦ 前端行为（来源切换、请求体、结果覆盖、老响应兼容）—— 同样带**对照组**。


前端不可能"写完就算完" —— 95 KB 的 JS 里一个括号错，用户看到的就是白屏。
**交付前一定要过一遍 `node --check`（或等价的语法闸门）**，不要靠"后端能返回 200"来判断前端没问题
（静态文件能正常返回 ≠ JS 能执行）。

### 追加（v0.2.4）：日志模块四条反馈 —— 卡死 / 下拉误关 / 实时过滤 / 清屏

用户四条原文：①抓全量日志容易卡死界面（建议分批加载显示）；②应用下拉滚动查看时列表会自动关闭；
③启动后输关键词没有实时重新过滤（要考虑日志非常多的性能）；④新增清空界面日志按钮。

#### ① 卡死的根因与修法（`VIEWS['device.logcat']` 整个重写）

老实现**每收一行**就 `appendChild` + `box.scrollTop = box.scrollHeight`（一次强制回流）。
全量日志每秒几百行，界面自然冻住。新模型：

| 件 | 作用 |
|---|---|
| 内存缓冲 `rows`（上限 20000） | 行先入缓冲，旧的丢；丢了多少在状态条明说，不静默 |
| 合并刷新（150ms 一批） | 高频 `log` 事件只在定时器里渲染一次，一批一个 `DocumentFragment` |
| **窗口化渲染**（DOM ≤ 500 行） | DOM 里永远只挂一个窗口；吸底时走**追加路径**（一行都不重建），灌 21500 行 DOM 仍是 500 |
| 跟随 / 回看双模式 | 离开底部=回看：新行**完全不碰 DOM**，只在「回到底部」按钮上计数；点按钮或滚回底部=恢复跟随 |
| 顶到头再滚 = 回加载一页 | 「分批加载显示」：每次往前翻一页（500 行），锚在"原来第一行"上不跳屏 |

**回看计数必须单独记（`newSinceLook`）**：缓冲满了以后 `view.length` 被 20000 封顶，
用"view.length − 已显示"算新行数**恒等于 0** —— 「回到底部」按钮永远不出现。
这个 bug 是行为验证抓出来的（第一次跑 verify28.js 时 7 个 FAIL 里有它）。

#### ② 下拉误关：一行监听的锅

`pkgCombo` 用 `window.addEventListener('scroll', close, true)` 在**捕获阶段**关面板，
而滚动面板自己的列表也会产生 scroll 事件（target 在面板里）→ "翻看列表"="关闭列表"。
修法：`if (panel.contains(e.target) || e.target === panel) return;` —— 页面滚动照旧关，
面板内部滚动放行。

#### ③ 实时过滤：把过滤从服务端搬到本地

老实现把 `level`/`filter` 传给 logcat 流 —— 是"**启动时定死**"的，改关键词就得重开流。
现在流只带 `pkg`/`device`，**级别+关键字在本地对缓冲过滤**（250ms 防抖），流不停、改完立即生效；
日志再多也只是"对 20000 行数组做一次子串过滤 + 重算 500 行窗口"，毫秒级。
后端 `stream/snapshot` 的 `level/filter_kw` 参数**原样保留**（CLI 和别的调用方还在用）。

#### ④ 清屏 ≠ 清缓冲

新增「清屏」：只清界面缓冲与显示，日志流继续接收（提示行里写明白）。
原有「清缓冲」是设备端 `logcat -c`，两个按钮并排、title 里说明区别。

**验证** `tmp/verify28.py`（**28 条断言**）+ `tmp/verify28.js`（**34 条**）：
js 侧是假 DOM 真跑新视图 + 真 `pkgCombo`：灌 1500/21500 行断言 DOM 恒 500、最后一行恒最新、
状态条数字不撒谎；过滤可逆；回看时 DOM 零抖动 + 按钮报数；分批回翻窗口前移；清屏后续流正常；
面板内滚动不关/面板外滚动关；两个**对照组**（老实现 1500 行 DOM=1500、旧关闭逻辑无视 target）
证明测试抓得住这两类 bug。py 侧：结构审计（类名↔CSS、pkgCombo 形状、流参数无 level/filter、
后端参数保留）+ 沙箱服务端到端（真机快照/SSE 流/清缓冲）。
harness 教训：**假 DOM 的保真度直接决定报告可信度** —— `input.value` 默认是 `''` 不是 `null`、
`scrollTop` 赋值会被浏览器钳制到 `scrollHeight − clientHeight`、`el.children` 真实存在。
第一版 7 个 FAIL 里 4 个是 harness 造的假象，逐个核对"真浏览器会不会这样"才分得清。

## 5. 还没做 / 已知限制

- **`ffmpeg` 未安装** → 录屏转 GIF 不可用（界面会红标提示，不影响其他功能）
- **push 到设备**只在 CLI 里开放（`file push`），Web 界面刻意只做 `ls` / `pull`，避免误传文件
- **签名的"有效性"不做断言** —— 自家解析只给指纹；要权威结论需勾选走 `apksigner`
- `wizard`（分步向导）渲染策略已在 `registry.py` 里预留，但当前 34 个能力都没用到
- **设备 dumpsys 快路径与本地解析的签名标识算法不同，不能直接比**（见 §2.3），界面只提示"值得留意"
- **原生目录对话框依赖 tkinter（或 PowerShell）**：managed Python 3.13 没带 tkinter，会自动回退到系统
  Python 3.12（探测链三段都记在 `doctor` 的 `tkinterTried` 里）。两个后端都不可用时，
  Web 界面走**页面内的目录浏览器**（`/api/fs/ls`），功能不降级
- **Intent extras 的字段名是 `key` / `value` / `type`**：`to_am_args()` 会跳过 `key` 为空的 extra
  （宁可不发，也不发 `--es "" ""`），所以字段名写错**不会报错、只会静默丢参数**。改前端时注意
- **右键卡片"推给主控台"只在主控台页面开着时才生效**（判定窗口 10 秒，见 §3 v0.2.1）。
  页面没打开时不会硬推，而是自动降级成独立卡片 —— 代价是会在浏览器里多开一个标签页，
  但**保证看得见**。这也是有意的取舍：静默失败比多一个标签页糟得多
- **「与设备已装应用对比」只对比 base.apk**：split 安装（base + 若干 config/feature 拆分包）
  的其余拆分包不参与比对，界面上会显式提醒。要全量对比请先「导出已装 APK」再走两个本机文件
- **设备侧的"按需读取"依赖 `adb exec-out dd`**（Android 6+ 都有）。个别 ROM 上拿不到时
  会自动退回 `adb pull` 到临时目录再解析，结论一样，只是慢一点、多一次整包搬运
- `tmp/` 下的验证脚本可随时清理，不影响运行。其中 `verify1`（CLI）/`verify2`（端到端真机）/
  `verify5`（路由↔注册表↔前端对齐）/`verify6`（断开抗性）/`verify7`（冷启动+单实例）/`verify24`
  （v0.2.0 全链路）/`verify25`（右键可见性）/`verify27`（双包对比·含设备）/
  `gate24`/`gate25`/`gate26` 是可复跑的回归集，建议留着

## 5.5 一键启动慢的根因与修复（v0.2.5）

用户反馈：双击 `start.bat` 要等十几秒才见服务。实测定位（`tmp/verify29.py`）：

- **根因**：`stop_all()` 要扫 `5170~5179` + 配置端口 + server.json 端口（约 12 个）找孤儿实例，
  对每个端口无脑发 HTTP `/api/health` 探活。而**本机环境对回环的关闭端口 refused 特别慢**
  （实测每次 **~1.5s**，走满 timeout；`start()` 的注释里早写过这个坑，但 `stop_all()` 漏修）。
  12 × 1.5s ≈ **15s 纯白等**，`web status` 指向死实例时也要白等 1 次。
- **修复**：和 `start()` 对齐 —— **先 `_is_port_free()`（bind 测试，~0ms）后探活**：
  端口空着就不可能有实例，HTTP 请求直接省掉。`stop_all()` 与 `status()` 两处。
- **实测对比**：有实例时 `web stop` **14.9s → 1.4s**；restart 全链路（stop+start）约 3s。
- 不变的语义：真正被占用的端口仍会照常探活/关停；别人占的端口（非本工具实例）不会误杀
  （verify29 C4 专门起了一个"陌生人" HTTP 服务验证）。
- **过程教训（又一个）**：两个 patch 脚本**并行**执行，同时读原文件、各自 replace 后写回，
  后写的把先写的覆盖了（丢更新竞态）——而两个脚本都各自打印了"patched"。**同一文件的
  多处修改必须串行**，写完必须**回读确认**（这次就是靠回读断言抓到的）。

## 5.6 打包与托盘宿主（v0.2.6）

需求原话：写 win / mac 两个打包脚本；打出来的程序双击即后台起服务 + 托盘菜单
（右键退出 / 重启服务等），显示启动状态；已启动就不再起服务（单例）。

**交付物**

| 文件 | 作用 |
|---|---|
| `apkparser/tray.py` | 托盘宿主本体（`APKConsole.py` 是根入口，只做转发 —— PyInstaller 分析脚本只把脚本所在目录放进 sys.path，入口放包内 `import apkparser` 就断了） |
| `package_win.py` | Windows 打包：自动补依赖 → PyInstaller onedir+windowed → 内嵌冒烟（health + 单例）→ zip |
| `package_mac.py` | macOS 打包：同上，`.app` 产物 + ad-hoc 签名（尽力而为）+ zip |
| `tmp/verify30.py` | 托盘服务面回归（8 条断言） |

**关键决策**

- **onedir 不用 onefile**：onefile 每次启动解压到临时目录，白多几秒 —— v0.2.5 刚把
  启动从十几秒修到几秒，不能在打包这步还回去。
- **托盘 = pystray + Pillow（仅托盘层）**：核心解析仍然零第三方依赖；两个包缺失时
  优雅降级成控制台常驻（源码环境无 GUI 也能调试服务逻辑）。
- **单例的职责划分**：端口上已有实例 → 第二个进程打开页面后**自己退出**，
  托盘只留在第一个进程。服务面复用 `server.start()` 的探测逻辑（先 bind 后探活）。
- **`stop_local()` / `restart_local()` 新增在 server.py**：托盘要在**同进程内**停/起
  服务，而 `request_shutdown()` 会 `os._exit(0)` 杀整个进程（为 HTTP 应答设计的），
  托盘不能用 —— 这是两个语义，不能混。
- **frozen 路径适配**（`paths.py` / `server.py`）：
  - `project_root()`：Windows frozen = exe 同级目录（**便携式布局**，output/logs/cache
    跟着程序文件夹走）；mac = 用户级数据目录（.app 包内不可写也不该写）
  - `STATIC_DIR`：源码布局优先，frozen 回退 `_MEIPASS/apkparser/web/static`
- **图标程序化生成**（Pillow 画圆角方块 + APK 字样，绿=运行/灰=停止），免维护
  二进制图标资源；Windows 构建时顺手生成 `.ico`。
- 状态显示三处：托盘 tooltip、菜单首行（disabled 状态行）、启动/重启后的气泡通知。
- `APKCONSOLE_NO_OPEN=1` 环境变量：自动化测试时抑制"自动开浏览器"。

**验证**

- `tmp/verify30.py`：8 PASS —— ①~④ 跨进程（起服务/常驻/第二实例自动退出/互不影响）、
  ⑤~⑦ **同进程** restart_local（同 pid 停+起）/ stop_local（服务下线进程不死）/ 再启动。
  过程教训：⑤ 的第一版在**另一个进程**里调 `restart_local`，`_server` 是模块级全局，
  辅助进程里它是 None → `start()` 走 alreadyRunning 分支返回"成功"—— **假阳性**。
  进程内语义必须进程内测。
- 真实构建：`package_win.py` 在本机全绿（构建 14s + 冒烟 health OK + 单例 OK）；
  frozen 产物实测 `/`、`/app.js`（157KB，含最新代码）均 200。
- 托盘 GUI（图标外观/右键菜单）无法自动验证，需人工双击确认。

**打包版的已知边界**

- 右键菜单注入、`start.bat` 一键启停这类"和源码树绑定"的功能在打包版里不可用
  （exe 旁边没有 apktool.py / start.bat）；打包版的主入口就是托盘。
- adb 仍从 PATH / 常见位置查找（`finders.py`），打包版不带 adb。

## 6. 一键启停脚本（v0.1.1 追加）

| 文件 | 作用 | 说明 |
|---|---|---|
| `start.bat` | 一键启动 | **restart 语义**：先停掉上一次的服务再启动（`web restart --foreground`）。控制台窗口即服务本体，关窗口/Ctrl+C 即停止；浏览器自动打开 |
| `stop.bat` | 一键停止 | `web stop` |
| `run-web.cmd` | 老入口（兼容） | **委托给 start.bat**，被 `routes.py` 脚本清单等引用，不能删 |
| `stop-web.cmd` | 老入口（配对） | 委托给 stop.bat |
| `run-web.sh` | macOS/Linux 启动 | 已对齐为 `web restart` |

- CLI 新增 `web restart`（`--port` / `--no-open` / `--foreground`）：
  先 `stop()`（旧实例不存在或残留死 pid 的 server.json 都不算错）→ `wait_port_free()` 等端口释放 → 再走正常 `start()`。
  `server.py` 新增 `wait_port_free(port, timeout)`。
- **bat 文件里的提示文案只用 ASCII**：cmd 按 OEM 代码页读 bat，UTF-8 中文会乱码；
  中文提示交给 Python 自己输出（`run-web.cmd` 旧版用 `chcp 65001` 也能对，但统一走 Python 更省心）。
- **Python 探测带"微软商店 stub 防御"**：`where python` 找到的可能是 WindowsApps 的假 python
  （运行只弹商店、退出码非 0），所以每个候选都要过一遍 `-c "import sys"` 真跑通才算数，
  最后兜底 `%LOCALAPPDATA%\Programs\Python\Python312\python.exe`。
- 端到端实测（`tmp/verify8.py` / `verify9.py`）：旧实例 pid 11268 在 5173 → 双击 start.bat 后
  旧实例被杀、新实例 pid 12848 上线 5170；stop.bat 后服务下线。委托链路 run-web.cmd/stop-web.cmd 同样验证通过。

> `tmp/verify26.js` 是"**行为**验证"的样板：它不 grep 源码，而是把 app.js 里真实的
> `parseOwnTab` / `apkInfoView` 抠出来、配假 DOM 真跑，数页面上有几份结果。
> 关键在于它同时跑一遍**旧实现当对照组**（必须数出 2 份）—— 没有对照组的 PASS 说明不了
> 任何事，因为"断言写错"和"代码正确"在报告里长得一模一样。

> `tmp/verify27.js` 踩了同类 harness 的一个坑：**漏注入一个依赖**（`deps.renderDiff`）后，视图
> 里的 try/catch 把异常吞成了一句红字提示，报告上表现为"结果卡片数 = 0"——**和真 bug 一模一样**。
> 所以抠源码型 harness 要遵守两条：① `deps` 按视图实际引用逐一对齐，缺谁都不行；
> ② 断言失败时把**页面上的异常提示原文**一起打出来，能一眼分出"代码错了"还是"测试自己错了"。

> `tmp/verify25.py` 是**可见性**闸门，管的是"用户到底看不看得见"。
> 它盯死一条不变式：**主控台进程活着但页面没在看时，右键必须退回浏览器卡片，
> 而且一条都不许 POST**。改 `ui/popup.py` 的 `show()` 或 `routes.py` 的
> `/api/health` / `/api/popup/pending` 之后必跑。
> 它会 monkeypatch `shell.open_url` 和 `paths.server_file()`，所以**不会**真的
> 弹浏览器、也**不会**动用户真实的 `server.json`。

> `tmp/gate24.py` 是**修复形状**的闸门：不光查语法，还查"改名改彻底了没有"
> （例如 `self.ok` 一处不改，`snapshot()` 就会引用到没初始化的属性）。
> 它自己踩过一个坑值得记住：判断 `"st.ok" not in js` 会被 **`fast.ok`** 的子串命中，
> 这类断言一律用 `\bst\.ok\b` 词边界。

> `tmp/verify20.py` 的 §1 是**结构性审计**：它会把每个叶子子命令真的 `parse_args` 一遍，
> 再和 handler 源码里读的 `ns.xxx` 对照。加子命令 / 改 handler 之后务必跑它 ——
> #19 那种"少注册一个 dest"的 bug 只有它能提前抓到（`tmp/verify21.py` 覆盖 Web 出口）。
> 这两个脚本都自带自检，会证明自己不是空转。
