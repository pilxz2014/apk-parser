# APK Parser Toolkit — 需求设计稿

> 版本：v0.1（设计评审稿）
> 日期：2026-09-18
> 项目目录：`D:\bat\apk-parser`
> 一句话定位：**Android 开发/测试日常的「APK 解析 + 设备操控」桌面工具箱**，以鼠标原生操作（右键 / 双击 / 图形界面）为主，命令行与脚本为辅。

---

## 0. 名词与边界

| 名词 | 含义 |
|---|---|
| 本机域 | 不需要连接设备即可工作的能力（解析本地 APK、签名、图标提取、瘦身分析） |
| 设备域 | 必须连接 Android 设备（adb）才能工作的能力（已装应用、启动 Activity、录屏、安装） |
| 主控台 | 常驻的图形界面（本地 Web UI），承载复杂交互 |
| 轻弹窗 | 右键/命令行触发的轻量结果展示（无需常驻进程也能秒开） |
| 菜单注入 | 把工具入口注册进操作系统的右键菜单 / 打开方式 |

**明确不做（Non-Goals）**：
- 不做 APK 反编译成源码（不集成 jadx 级别能力，仅提供可选的「用外部工具打开」跳转）
- 不做设备 Root / 越狱相关能力
- 不做云同步、账号体系

## 1. 背景与目标

### 1.1 现状痛点

现在的工作流是「手动敲 adb 命令 + 翻文档 + 复制包名到记事本」，具体表现为：

1. **看一个 APK 的版本号/包名**要开 `aapt dump badging`，还得记得 aapt 在哪、参数怎么写；
2. **看已装应用**要 `adb shell pm list packages` 拿一堆包名，眼睛找包名，想启动某个 Activity 还得再 `pm dump` 翻 `MAIN/LAUNCHER`；
3. **启动一个非 Launcher 的 Activity**（比如内部测试页、Debug 页面）几乎没有趁手的图形化入口，`am start` 的 `-n` / `-a` / `--es` 参数全靠背；
4. **录屏/截图**零散命在不同工具之间（adb screencap / scrcpy / 录屏软件），产物路径混乱；
5. **装 APK** 要开终端敲 `adb install -r`，失败了只给一行 `INSTALL_FAILED_*` 错误码，还得去查是什么意思；
6. 这些操作**无历史、无复用**，同一个包名一天要复制十几次。

### 1.2 设计目标

| # | 目标 | 可衡量标准 |
|---|---|---|
| G1 | **看一眼就够**：APK / 应用的关键信息（包名、版本名、版本号、目标 SDK、签名、大小）在打开后 1 眼内可见 | 首屏信息区不超过 6 行，包名与版本名置于最顶 |
| G2 | **点两下就完成**：右键解析、双击安装、选中即启动 | 从右键到看到结果 ≤ 3 秒 |
| G3 | **零记忆负担**：所有 adb 参数都由界面生成并可实时预览完整命令 | 每个动作都能看到「将执行的命令」，且可复制 |
| G4 | **跨平台一致**：Windows / macOS / Linux 同一套代码，仅系统集成层做适配 | 核心层无平台判断分支 |
| G5 | **易扩展**：加一个新功能不需要改动既有界面代码 | 通过「能力注册表」声明式接入 |

### 1.3 设计理念

- **不需要常驻也能用**：右键/双击类操作在没有任何后台进程时也必须可用（走轻弹窗模式）。
- **一切皆可复制为命令**：界面上每个动作都对应一条真实命令，界面上直接可见、可复制，便于沉淀成脚本（衔接你已有的 `D:\bat\*.sh`）。
- **结果导向而非流程导向**：用户点「启动 Activity」，直接给结果 + 命令 + 日志，不搞多步向导。

## 2. 用户与典型场景

**Persona**：Android 应用开发者 / 测试工程师，机器上装了 adb、scrcpy，日常要处理多渠道变体 APK（ToC ~30+、ToB ~40+），需要在多台设备上反复验证。

### 场景 S1（右键解析）
打包目录里躺着一堆渠道 APK。我右键 `app-jxwgb-release.apk` → 菜单「APK 工具 / 解析信息」→ 浏览器立刻弹出一张信息卡：包名、版本名/号、渠道、签名指纹、ABI、最小/目标 SDK。**不用切终端**。

### 场景 S2（找已装应用）
平板连着线。我打开主控台，在搜索框敲 `xwsf`，列表实时过滤出 `com.jxw.xwsf`，右侧详情立刻显示版本、安装时间、数据目录占用。

### 场景 S3（启动任意 Activity）
选中的是 `com.jxw.xwsf`，我切到「启动器」页，看到：
- 可启动 Activity 列表（`MAIN/LAUNCHER` 的排在最前，标 ★）
- 可启动 Service 列表
我点 `WifiListActivity`，右侧参数面板自动带出 `-n com.jxw.xwsf/.ui.WifiListActivity`，我加了 `--es ssid "test"`，点「启动」，1 秒后提示启动成功，并显示 `am start -W` 的 `TotalTime`。

### 场景 S4（双击安装）
手边有个新包，我直接**双击 apk** → 弹出命令行窗口，实时滚动输出安装日志 → 结束打印绿字「安装成功 12.3s」或红字「失败：INSTALL_FAILED_VERSION_DOWNGRADE（设备上已装版本更高，需先卸载或用 -d 允许降级）」并给出「按 D 直接带 -d 重试」。

### 场景 S5（录制与截图）
要录一段复现视频。主控台「捕获」页点「开始录屏」，看到实时计时；复现完点「停止」，文件自动落到 `captures/` 并给出「打开所在目录 / 复制路径 / 转 GIF」三个后续动作。

### 场景 S6（沉淀为脚本）
我调好一条 `am start` 命令，点界面上的「复制命令」，粘进我自己的 `D:\bat\*.sh` 里——工具与脚本生态自然衔接。

### 场景 S7（签名核对）
客户说"装不上，报签名冲突"。我要确认设备上那个包和我手上的 APK 是不是同一个签名：
选中设备上的 `com.jxw.student.study` → 「签名」区块先秒出「方案 v2 · 签名标识 `da3a4721`」，
1 秒后补全证书主题与 SHA-256；再把本机 APK 拖进来比对，结论直接写「**不同签名**」，
并指出「设备端签名标识 `da3a4721` ≠ APK 端 `7f2b1c04`」——不用敲 `keytool`，也不用 root。

### 场景 S8（不 root 也不硬来）
换到一台限制了 `/data/app` 访问的 ROM，签名区块显示：
「该设备不支持免 root 读取已安装应用签名（`dumpsys` 无签名字段，pull 被拒绝）」，
并给一个「查看本机 APK 签名」的替代入口。**不申请 root、不给假数据**。

## 3. 功能地图

按「**是否需要设备**」划分为两个一级域，每个域下按能力聚类。这个划分既是导航结构，也是后续扩展的挂载点。

```
APK Parser Toolkit
│
├─ 🖥 本机域（Local，无设备也可用）
│   ├─ L1  APK 解析          包名/版本/权限/ABI/图标/★签名/渠道
│   ├─ L2  APK 分析          瘦身占比、方法数、★签名校验与比对、双包对比
│   └─ L3  APK 加工          图标提取、重签名(可选)、改名归档
│
├─ 📱 设备域（Device，需 adb）
│   ├─ D1  设备管理          多设备、无线连接、设备工具集
│   ├─ D2  应用管理          已装应用检索、详情、★已装签名、快捷操作
│   ├─ D3  启动器            Activity / Service / Broadcast / DeepLink
│   ├─ D4  捕获中心          截图、录屏、实时镜像、logcat、性能
│   ├─ D5  安装与分发        单装/批装/多机并发/失败诊断
│   └─ D6  文件与传输        push / pull / 设备文件浏览
│
└─ ⚙ 系统层（System）
    ├─ S1  菜单注入          右键菜单 / 打开方式 / 双击关联
    ├─ S2  全局设置          adb 路径、端口、产物目录、主题
    └─ S3  命令与脚本        CLI 契约、生成 .sh/.bat 模板
```

> ★ = 签名相关能力。**核心原则：已安装应用的完整签名信息，一律通过「把设备上的 APK 拉到本地自解析」获得，全程不申请 root。**
> 已用真机实测确认（Z21 / Android 13 / SDK 33）：`adb pull /data/app/…/base.apk` 免 root 可用，约 35 MB/s（54 MB 的包 1.47s）。
> 若某 ROM 上两条路都走不通，界面明确说明并停手，**不申请 root、不显示猜测值**。详见 [技术方案 §7.1](03-技术方案.md)。

## 4. 详细需求

优先级：**P0 = 必须**（第一版交付）、**P1 = 应当**、**P2 = 可选/后续**。

### 4.1 L1 本机 APK 解析

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| L1-1 | 解析 APK 基础信息 | P0 | 输出：包名、版本名、版本号(versionCode)、应用名(多语言取最佳匹配)、minSdk、targetSdk、compileSdk(如可得) |
| L1-2 | 首屏信息排序 | P0 | 包名、版本名/号固定在最顶部大字显示，其余信息在下方分区 |
| L1-3 | **签名信息**（本机 APK） | P0 | 显示签名方案(v1/v2/v3)、签名者数量、证书主题(DN)、SHA-256 / SHA-1 指纹、有效期、密钥算法与长度、是否 debug 签名 |
| L1-3a | 指纹分组与复制 | P0 | SHA-256 按字节分组显示（`A1:B2:C3:…`）便于肉眼比对；每项独立复制按钮 + 「复制全部签名信息」 |
| L1-3b | 签名验证结论 | P1 | `apksigner` 可用时给权威结论「签名有效 / 无效 / v2 签名被篡改」；不可用时明确标注「仅展示，未验证」，不暗示已验证 |
| L1-3c | 多签名者与签名谱系 | P2 | 支持多签名（多签名者 APK）与 `past signatures`（签名轮转历史）展示 |
| L1-4 | 权限清单 | P0 | 列出 uses-permission，并对**危险权限**加红色标记与中文说明 |
| L1-5 | 组件清单 | P0 | Activity / Service / Receiver / Provider 数量统计；可展开看列表；标出 exported=true 的组件（安全提示） |
| L1-6 | ABI 与原生库 | P0 | 列出 `lib/` 下所有 ABI 目录及各自 so 文件数与体积 |
| L1-7 | 文件构成 | P1 | 各顶层目录/大文件体积占比（Top 10），用于瘦身判断 |
| L1-8 | 图标提取 | P1 | 从 mipmap/drawable 中取出最大尺寸图标并在界面显示，可另存 PNG |
| L1-9 | 渠道信息 | P1 | 识别常见渠道标记（`META-INF/channel_*`、`channel` 文件、`UMENG_CHANNEL` meta-data），显示渠道名 —— 针对多渠道变体场景 |
| L1-10 | 解析方式自适应 | P0 | 优先纯 Python 解析（零依赖）；检测到 `aapt2`/`aapt` 时自动用它做交叉校验，二者不一致时在界面给出提示 |
| L1-11 | 批量解析 | P1 | 支持 Ctrl/Shift 多选一批 APK，输出可排序对比表格，导出 CSV |
| L1-12 | 右键即解析 | P0 | 右键菜单 → 弹出信息卡（详见交互稿） |

### 4.2 L2 APK 分析

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| L2-1 | 双包对比 | P1 | 选两个 APK，逐项 diff（版本、权限增减、ABI 增减、体积变化、签名是否一致），差异高亮 |
| L2-2 | 与设备已装版本对比 | P1 | 选中本机 APK + 设备已装同名包，判断「可升级 / 同级 / 降级 / 签名冲突」并给结论 |
| L2-3 | dex 方法数 | P1 | 统计 dex 中方法引用数（判断 65K 限制风险） |
| L2-4 | 体积明细排序 | P2 | 按文件大小 Top N 列表，支持导出 |

### 4.3 L3 APK 加工

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| L3-1 | 提取图标为 PNG | P1 | 输出到 `output/icon_<包名>.png`，支持多尺寸 |
| L3-2 | 复制包名/版本串 | P0 | 右键菜单与界面均提供「复制包名」「复制 包名+版本」 |
| L3-3 | 归档重命名 | P2 | 按 `包名_版本名_版本号.apk` 规则复制一份到指定目录 |

### 4.4 D1 设备管理

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| D1-1 | 设备列表 | P0 | 显示序列号、型号、Android 版本、SDK、连接方式(USB/WiFi)、状态；每 3~5 秒自动刷新，插拔自动跟随 |
| D1-2 | 多设备切换 | P0 | 顶栏下拉切换，全局生效；已离线设备的请求自动回退到唯一在线设备并提示 |
| D1-3 | 无线 adb 连接 | P1 | 一键 `adb tcpip 5555` + `adb connect ip:port`；显示当前 IP；记住历史 IP 列表 |
| D1-4 | 设备工具集 | P1 | 强制停止应用、清除数据、卸载、禁用/启用组件、重启应用、截图、重启设备、进入 Recovery/Fastboot(需确认) |
| D1-5 | 系统信息 | P1 | 分辨率、DPI、CPU/ABI、内存、存储占用、电量、温度、开发者选项跳转 |
| D1-6 | 网络模拟 | P2 | 模拟弱网/断网（`svc data`、`settings put global`） |
| D1-7 | 屏幕参数 | P2 | 快速改分辨率/DPI/语言/时区（带一键还原） |

### 4.5 D2 应用管理

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| D2-1 | 已装应用列表 | P0 | 列出所有包名 + 应用名；**默认只显示第三方应用**，可切换「含系统应用」 |
| D2-2 | 模糊过滤 | P0 | 输入即过滤，**同时匹配包名与应用名**，大小写不敏感，空格分词（多个关键词 AND） |
| D2-3 | 应用详情 | P0 | 包名、版本名/号、安装时间/更新时间、安装路径、目标 SDK、UID、是否系统应用、是否可卸载、数据目录大小 |
| D2-4 | 详情首屏排序 | P0 | 与 L1-2 一致：包名 + 版本名/号在最顶部 |
| D2-5 | 应用快捷操作 | P1 | 启动主界面、强制停止、清除数据（二次确认）、卸载、禁用、导出 APK 到本机、查看权限 |
| D2-6 | 导出已装 APK | P1 | `pm path` + `pull`，命名 `包名_版本名.apk` |
| D2-7 | 应用列表导出 | P2 | 导出 CSV（包名、版本、安装时间） |
| D2-8 | 包名关键字高亮 | P1 | 搜索命中的字符在列表中高亮 |
| **D2-9** | **已装应用签名信息** | **P0** | 显示该应用**在设备上**的签名：签名方案(v1/v2/v3)、签名标识、证书主题(DN)、SHA-256/SHA-1 指纹、有效期、密钥算法与长度、是否 debug 签名；与 L1-3（本机 APK 签名）**共用同一套展示组件与文案** |
| D2-10 | 签名两路获取策略 | P0 | **快路径**：`dumpsys package <pkg>` 解析 `apkSigningVersion` + `signatures=[…]`，约 0.3s 先出「方案版本 + 签名标识」，界面立即有内容；**完整路径**：`pm path` → `adb pull` 设备上的 `base.apk` → 本地解析出 DN / SHA-256 / 有效期。带进度与可取消 |
| D2-11 | 签名结果缓存 | P1 | 完整签名结果按 `包名 + versionCode` 缓存到 `cache/signature/`，二次查看零耗时；**与「导出已装 APK」复用同一次 pull 与同一份本地文件**，不做重复下载 |
| D2-12 | 免 root 不可得时的降级 | P0 | 若 `dumpsys` 无签名字段**且** pull 被拒（受限 ROM / 沙箱），界面明确显示「该设备不支持免 root 读取已安装应用签名」，并给出原因（哪一步失败、原始输出）与替代入口（改为查看本机 APK 签名）。**绝不申请 root、绝不用占位符或猜测值填充** |
| D2-13 | 签名一致性对比 | P1 | 支持三组比对：「本机 APK ↔ 设备已装」、「设备 A ↔ 设备 B（同包名）」、「同一设备上两个包是否同签名」；输出结论 **同一签名 / 不同签名 / 无法判定**，并列出判定依据字段（比较标识、SHA-256、DN） |
| D2-14 | 复制签名信息 | P0 | 每个字段独立复制；另有「复制签名摘要」（一行式，如 `com.jxw.student.study v2.1.0(210) SHA-256:AB:CD:…` 便于贴群里）与「复制完整签名块」 |
| D2-15 | split APK 处理 | P1 | App Bundle 安装的应用 `pm path` 会返回 base + 多个 split；签名只取 `base.apk`（签名仅存在于 base），避免多文件下载与误判 |
| D2-16 | 签名异常预警 | P1 | 检测到 debug 签名 / 签名有效期已过期 / 存在 past signatures（签名轮转）时，在签名区块顶部给出黄色提示 |

### 4.6 D3 启动器（重点）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| D3-1 | 可启动 Activity 列表 | P0 | 解析 `pm dump <pkg>` 或 `dumpsys package <pkg>`，列出所有 Activity；其中含 `MAIN`+`LAUNCHER` intent-filter 的标记 ★ 并置顶 |
| D3-2 | 可启动 Service 列表 | P0 | 列出所有 Service；标记 `exported=true` 的可外部启动项 |
| D3-3 | 组件状态标记 | P1 | 标记 `enabled=true/false`、`exported=true/false`，禁用/未导出项启动会失败，需在界面上预警 |
| D3-4 | 过滤与搜索 | P0 | Activity/Service 列表各自支持模糊过滤 |
| D3-5 | 启动参数编辑器 | P0 | 见 4.6.1 |
| D3-6 | 命令实时预览 | P0 | 参数任一变更，底部命令预览同步更新，可一键复制 |
| D3-7 | 启动并计时 | P1 | 用 `am start -W` 启动，回显 `ThisTime / TotalTime / WaitTime` |
| D3-8 | 启动并抓日志 | P1 | 启动同时按包名过滤 logcat，返回启动后 X 秒内的日志 |

**4.6.1 启动参数编辑器（详细）**

分组表单，每组可折叠：

| 分组 | 字段 | 生成的 adb 片段 |
|---|---|---|
| 目标 | 组件类型(Activity/Service)、包名、组件全名 | `-n pkg/.Cls` |
| Action | action、data URI、MIME type | `-a xxx -d xxx -t xxx` |
| Category | 多选（LAUNCHER / DEFAULT / BROWSABLE / HOME…）+ 自定义 | `-c xxx` |
| Flags | 复选（`FLAG_ACTIVITY_NEW_TASK` / `CLEAR_TOP` / `SINGLE_TOP` / `CLEAR_TASK` / `EXCLUDE_FROM_RECENTS`…） | `-f 0x10000000` |
| Extras | 动态行列表：类型（string/int/bool/float/long/uri/arrayList）+ key + value | `--es key val` / `--ei` / `--ez` / `--ef` / `--el` / `--esn` |
| 启动方式 | 普通 / `-W` 计时 / 强制 `--user 0` / `--activity-clear-top` | |
| 高级 | 允许非导出组件(需 root，灰置) / 超时时间 | |

实时预览区示例：

```
adb -s AQLCCP5A23403810 shell am start -W \
  -n com.jxw.xwsf/.ui.WifiListActivity \
  -a android.intent.action.VIEW -d "xwsf://scan?ssid=test" \
  -c android.intent.category.DEFAULT \
  -f 0x10000000 \
  --es ssid "test" --ez autoScan true --ei timeout 5000
```

## 5. 非功能需求

| 类别 | 要求 |
|---|---|
| **跨平台** | 核心逻辑纯 Python 3.8+，零第三方依赖（可选增强项才用 aapt/scrcpy/ffmpeg）。系统差异全部收敛到 `platform/` 包，业务代码不得出现 `if windows` 判断 |
| **启动性能** | 轻弹窗（右键解析）端到端 ≤ 3s；主控台冷启动 ≤ 2s |
| **稳定性** | 所有 adb 调用带超时（默认 20s，长任务可配）；设备离线/未授权/多设备歧义都要有明确文案，不允许「空白页 + 无报错」 |
| **可观测** | 主控台底部长驻「命令日志」抽屉，记录每条实际执行的命令、耗时、退出码、stderr —— 出问题第一现场可查 |
| **安全** | 默认仅监听 `127.0.0.1`；服务端对传入路径做真实路径校验，避免越权读文件；危险操作（清数据、卸载、重启）二次确认 |
| **权限边界** | **全程不申请、不依赖、不引导 root**。已装应用签名等敏感信息只走免 root 路径；两条路都不通时，明确说明失败在哪一步并停止，不用假值兜底、不"尽力而为"地猜 |
| **可扩展** | 新能力通过「能力注册表」声明，前端自动生成页签与操作按钮，无需改框架代码（详见技术方案） |
| **无污染** | 不改动系统 PATH、不写 system 目录、不装全局 pip 包；仅写 HKCU 注册表项（可一键卸载） |

## 6. 可扩展性设计原则

为了「方便以后扩展」，从第一版就固化三条约定：

1. **能力即数据**：每个功能是一个 `Capability` 描述对象（id / 名称 / 分组 / 图标 / 参数表单 schema / 执行器 / 是否需设备 / 风险等级）。前后端都读同一份描述。
2. **三层分离**：`core`（纯逻辑，无 IO 副作用）→ `cli`（命令入口）→ `web`（HTTP 包装）→ `ui`（渲染）。新增能力只加 core + 注册，界面自动出现。
3. **协议稳定**：CLI 与 HTTP 的输出格式一旦发布就向后兼容（只增字段不删字段），保证外部脚本不会被工具升级打断。

**扩展示例（加「启动耗时统计」）**：
```
1) core/launcher.py 里加函数 launch_timed(...)
2) 在 registry.py 注册 Capability(id="launch.timed", ...)
3) 完成 —— CLI 自动出现 `apktool.py launch --timed`，界面自动多一个按钮
```

## 附录 A：常见安装失败码 → 中文解释（D5-5 词表）

| 错误码 | 中文说明 | 建议处置 |
|---|---|---|
| `INSTALL_FAILED_ALREADY_EXISTS` | 已存在该应用 | 勾选「覆盖安装 -r」 |
| `INSTALL_FAILED_VERSION_DOWNGRADE` | 设备上版本更高，不允许降级 | 加 `-d` 允许降级，或先卸载 |
| `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | 签名不一致，无法覆盖 | 先卸载原应用（数据会丢） |
| `INSTALL_FAILED_INSUFFICIENT_STORAGE` | 存储空间不足 | 清理设备空间 |
| `INSTALL_PARSE_FAILED_NO_CERTIFICATES` | APK 未签名或签名损坏 | 重新签名 |
| `INSTALL_PARSE_FAILED_INCONSISTENT_CERTIFICATES` | 与已装版本签名证书不一致 | 先卸载 |
| `INSTALL_FAILED_TEST_ONLY` | 是 test-only 包 | 勾选「允许测试包 -t」 |
| `INSTALL_FAILED_ABI_INCOMPATIBLE` | ABI 与设备不匹配 | 换对应 ABI 的包 |
| `INSTALL_FAILED_OLDER_SDK` | 设备 Android 版本低于 minSdk | 换设备或改 minSdk |
| `INSTALL_FAILED_NO_MATCHING_ABIS` | 没有匹配的原生库 | 检查 so 架构 |
| `INSTALL_FAILED_USER_RESTRICTED` | 被设备策略/厂商限制 | 检查「安装未知应用」权限、关闭纯净模式 |
| `INSTALL_CANCELED_BY_USER` | 设备上取消了安装确认 | 重新安装并在设备上确认 |
| `INSTALL_FAILED_VERIFICATION_FAILURE` | 设备校验失败 | 临时关闭「验证应用」 |
| `INSTALL_FAILED_DEXOPT` | dex 优化失败 | 清空间或换包 |
| `INSTALL_FAILED_CONTAINER_ERROR` | 装到 SD 卡失败 | 改为装到内部存储 |
